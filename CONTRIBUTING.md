# Contributing

Thanks for helping. This file is for people and coding agents changing the plugin itself. `AGENTS.md` holds the same rules in short form.

## Setup

You need Node 20 or newer and Git.

```bash
npm install          # Prettier, and the Git hooks switched on
npm run check        # Prettier, then the tests
npm run validate     # claude plugin validate --strict
```

`npm run validate` runs a pinned Claude Code version, so CI gives the same answer every day. To bump it, set the version in `package.json`'s `validate` script to the one `npm view @anthropic-ai/claude-code version` prints, and run it once locally.

The runtime has no dependencies. Prettier is the only devDependency, and it stays that way.

To try your copy of the plugin in Claude Code for one session, start it with `claude --plugin-dir .` from the repo root.

## How we work

- Trunk-based: `main` is always green and moves only through a pull request. Branch from an up-to-date `main` (`feat/...`, `fix/...`, `docs/...`, `chore/...`), one topic per branch.
- Write the test first, then the change. Run `npm run check` and read the result before you open the pull request.
- Conventional commits: `feat(scripts): ...`, `fix(skills): ...`, `docs: ...`, `chore: ...`, `test: ...`. The pull request title is one too, since it is squash-merged.
- Docs are part of the change: if it makes the README, `AGENTS.md` or a skill wrong, fix them in the same pull request.
- Copy rules for skills, templates and the README: plain words, sentence case headings, no em dashes, no exclamation marks.
- The eval cases in `evals/` call the model and cost money. CI never runs them. Run them by hand only when a skill's routing or output changed, as `evals/README.md` describes.

## Nothing personal, nothing secret

Nothing personal or secret enters the repo: no keys or tokens, no home-folder paths, no names or emails of people, no private notes. The guards below catch the common cases; the rest is on you.

## Guards

Every change passes the same guards, whoever writes it, a person or a coding agent. They run twice:

- **On every commit.** The Git hooks in `.githooks/` are switched on by `npm install` (`core.hooksPath`). `pre-commit` checks what is staged and `commit-msg` checks the message, so nothing bad becomes a commit.
- **In `npm test`.** `checks/guards.test.mjs` runs locally and in CI on every file Git would commit, so a skipped hook is still caught.

Claude Code is denied `--no-verify` and `-n` on a commit, changing `core.hooksPath`, editing `.githooks/` and editing or rewriting `checks/guards.mjs` (`.claude/settings.json`). Other agents get the same rule from `AGENTS.md`.

The guards:

- no keys or tokens: private key blocks; GitHub, Anthropic, OpenAI, Google, Stripe, npm, AWS, GitLab and Slack token formats; a Postgres URL with a real password (local hosts and short placeholders pass); a MySQL or MongoDB URL with a password
- no `.env` file of any name (`.env`, `.env.local`, `.env.production`); only `.env.example` is committed
- no home folder: no path into a user's home folder on macOS, Linux or Windows, so a path committed from another laptop still fails CI
- no AI tool credited as an author, in files or commit messages: a `Co-Authored-By` trailer naming a tool or an address at an AI company, and a "Generated with" or "Generated by" line, linked or not
- no file over 1 MB
- a commit message that is a conventional commit

If a guard trips:

- **A key:** remove it. If it was ever pushed, rotate it with its provider; deleting it from Git is not enough.
- **A path or an attribution line:** fix the file, or whatever wrote it.

Fix the cause. Never weaken a guard, never commit with `--no-verify`, never change `core.hooksPath`.

## Adding a skill

1. A folder under `skills/<name>/` with a `SKILL.md`. The name is one plain word that says what the skill does, and it appears as `/crocotaste:<name>`.
2. Frontmatter keys: `name` (equal to the folder), `description` (what it does and when to use it, under 1024 characters), `when_to_use` (trigger phrases), and `argument-hint` when the skill takes an argument.
3. The `SKILL.md` stays under 500 lines. Detail goes into `references/`, files the skill copies go into `templates/`, and every path the skill names must exist.
4. A test in `checks/`: add the folder to the list in `checks/manifest.test.mjs`, and test what the skill promises. `checks/skills.test.mjs` already checks the frontmatter, the length and the paths.
5. The skill ends by naming the next one in the chain, if there is one, and never overwrites a user's file without asking.
6. An eval case under `evals/` for a skill that should fire on a plain request.

## Pull requests

Fill in the template: a summary, the evidence (`npm run check`, `npm run validate`, any dry run of a skill), and the docs you touched. Never credit an AI tool as an author, in commits or in the pull request.

Questions and ideas: open an issue.
